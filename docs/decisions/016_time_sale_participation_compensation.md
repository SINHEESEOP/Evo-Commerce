### 문제 상황
타임세일 참여 처리를 Redis 원자적 연산(Lua 스크립트)으로 재설계하면서, 잔여 수량 차감과 중복 참여 확인은 Redis 안에서 먼저 확정되고 그 결과를 아웃박스에 기록하는 것은 별도의 독립적인 DB 쓰기가 됐다. 아웃박스 기록이 DB 장애 등으로 실패하면, 이미 Redis에 커밋된 차감·중복 등록을 되돌릴 방법이 없어 참여 슬롯이 어떤 주문·참여 기록도 남기지 못한 채 영구히 사라졌다(ISSUE-33).

### 검토한 대안
- **아웃박스 저장을 즉시 몇 차례 재시도한다**: 요청 스레드 안에서 재시도하면 그만큼 응답이 늦어지고, 애초에 참여 처리를 비동기로 분리한 목적(요청 스레드가 DB 트랜잭션에 오래 묶이지 않게 하는 것)과 어긋난다. 게다가 재시도가 모두 실패하면 결국 같은 문제로 돌아온다.
- **Redis 예약을 아웃박스 기록 이후로 미룬다(순서를 바꾼다)**: 실패 시나리오가 반대 방향으로 뒤바뀔 뿐 문제 자체는 사라지지 않는다 — 아웃박스에는 참여 사실이 기록됐는데 정원 초과 여부를 사후에 확인해야 하는 상황이 새로 생긴다.
- **아웃박스 저장 실패 시 Redis 쪽 변화를 명시적으로 되돌리는 보상 트랜잭션을 실행한다**: 실패를 흡수하려 하지 않고, 이미 확정된 앞 단계를 되돌려 시스템을 실패 이전 상태로 복구한다.

### 결정 및 이유
세 번째 대안(보상 트랜잭션)을 선택했다. Redis 쪽 실패는 동기 호출이라 즉시 감지할 수 있고, 되돌리는 연산(참여자 집합에서 제거 + 잔여 수량 원복)도 새로운 Lua 스크립트 하나로 단순하게 표현된다 — 재시도로 요청 스레드를 붙잡아두거나 순서를 바꿔 실패 시나리오를 다른 곳으로 옮기는 것보다, 실패를 감지한 그 자리에서 되돌리는 쪽이 코드도 단순하고 사용자 경험도 명확하다(즉시 "일시적으로 처리하지 못했다"는 응답과 함께 재시도가 실제로 가능한 상태가 된다).

### 적용 결과
`TimeSaleFacade.participate()`가 아웃박스 저장을 `try-catch`로 감싸고, 실패 시 `releaseParticipation()`(보상 Lua 스크립트)을 호출한 뒤 `PARTICIPATION_TEMPORARILY_UNAVAILABLE`을 반환하도록 했다. 실제 DB 장애 상황을 흉내 내 검증한 결과, 실패 직후 Redis의 잔여 수량과 참여자 집합이 정확히 원래 상태로 복구됐고, 이후 같은 사용자가 재시도했을 때 정상적으로 참여에 성공했다. 컨슈머가 참조하는 이벤트/사용자가 존재하지 않는 것 같은 영구적 실패를 일시적 실패와 구분해 재시도 없이 즉시 DLQ로 보내는 것, 그리고 보상 스크립트 자체가 실패하는 이중 장애 상황에 대한 재조정(reconciliation) 절차는 이번 결정 범위에 포함하지 않았다.

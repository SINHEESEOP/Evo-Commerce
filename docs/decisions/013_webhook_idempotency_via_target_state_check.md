### 문제 상황
`handlePaymentWebhook()`이 주문 상태를 확인하지 않고 매번 `order.pay()`를 호출해, 같은 결제 완료 이벤트가 중복 전달(재시도)되면 두 번째 호출부터 `INVALID_STATUS_TRANSITION` 예외가 발생했다. Toss는 200이 아닌 응답을 실패로 간주해 계속 재전송하므로, 같은 오류가 반복됐다.

### 검토한 대안
- 이벤트 자체에 고유 식별자를 부여하고, 처리한 이벤트 ID를 별도 테이블에 기록해서 "이미 처리한 이벤트인지" 추적하는 방식(멱등성 키)
- 웹훅 처리 전에 주문의 현재 상태가 이미 목표 상태(`PAID`)와 같은지 확인해서, 같으면 아무것도 하지 않고 조용히 종료하는 방식

### 결정 및 이유
후자를 선택했다. 지금 이 프로젝트에서 웹훅으로 벌어지는 유일한 부수 효과는 `order.pay()`(상태 전이)뿐이고, 그 목표 상태는 이미 `Order` 엔티티가 갖고 있는 값이다. 별도의 이벤트 처리 이력 테이블을 새로 만들지 않아도, "지금 이미 그 목표 상태인가"만 확인하면 중복 호출을 안전하게 무시할 수 있다. 이벤트 ID 추적 방식은 웹훅에 딸린 부수 효과가 여러 개로 늘어나거나(예: 알림 발송처럼 상태와 무관하게 매번 실행되면 안 되는 작업이 생기는 경우) 진짜로 필요해질 것이다.

### 적용 결과
`handlePaymentWebhook()`이 `order.pay()`를 호출하기 전에 `order.getStatus() == OrderStatus.PAID`인지 먼저 확인하고, 이미 `PAID`면 그대로 반환한다. 같은 웹훅이 두 번 들어와도 두 번째 호출은 예외 없이 200으로 끝난다. 회귀 테스트로 같은 주문에 웹훅을 두 번 처리했을 때 예외 없이 `PAID` 상태가 유지되는지 검증했다.

이미 `CANCELLED`인 주문에 결제 완료 웹훅이 오는 경우는 이번 수정 범위에 포함하지 않았다 — 이건 "정상적인 중복 수신"이 아니라 결제와 취소가 경쟁하는 별도의 정합성 문제(`docs/wiki/Phase2_기획및설계.md`에서 이미 범위 밖으로 명시)라 지금 로직은 여전히 예외를 던진다.

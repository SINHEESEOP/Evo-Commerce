### 문제 상황
`OutboxEventPublisher.publishPendingEvents()`가 대기 중인 이벤트를 발행한 뒤 무조건 `SENT`로 표시해, 실제 알림 저장이 실패해도(리스너가 `@Async`라 예외가 호출자에게 전파되지 않음) 재시도되지 않고 조용히 유실되는 문제가 있었다(ISSUE-29).

### 검토한 대안
- 리스너의 `@Async`를 유지한 채, 리스너가 별도의 결과 테이블/콜백으로 성공 여부를 기록하고 스케줄러가 그걸 다시 조회해서 `SENT` 여부를 확정하는 방식
- 리스너에서 `@Async`를 제거해 스케줄러와 같은 스레드·같은 트랜잭션에서 동기 실행하고, 그 호출이 예외 없이 끝난 경우에만 `SENT`로 표시하는 방식

### 결정 및 이유
후자를 선택했다. 이 리스너의 유일한 호출자가 이제 `OutboxEventPublisher`뿐이라, `@Async`가 원래 의도했던 "요청 스레드를 블로킹하지 않는다"는 이점이 더 이상 의미가 없다 — 애초에 스케줄러 스레드는 사용자 요청과 무관하다. 별도의 결과 기록 테이블을 두는 방식은 "성공 여부를 어떻게 확인할 것인가"라는 문제를 다른 테이블로 옮길 뿐 근본적으로 해결하지 않고, 테이블 하나를 더 늘리는 비용도 크다. 동기 실행 + 같은 트랜잭션 커밋은 별도 인프라 없이 "발행 시도와 완료 확정을 한 트랜잭션으로 묶는다"는 아웃박스 패턴의 원래 취지에 가장 직접적으로 부합한다.

각 이벤트를 `TransactionTemplate.executeWithoutResult(...)`로 감싸 이벤트별로 독립된 트랜잭션을 열도록 했다 — 배치 전체를 하나의 트랜잭션으로 묶으면 한 이벤트의 실패가 영속성 컨텍스트를 오염시켜 이후 이벤트 처리에 영향을 줄 수 있기 때문이다(이 프로젝트의 `TimeSaleFacade.participate()`가 재시도마다 새 트랜잭션을 여는 것과 같은 이유).

### 적용 결과
`NotificationEventListener.handleOrderPaid()`에서 `@Async`를 제거하고, SSE 전송 실패(`IOException`)는 그 자리에서 개별적으로 잡아 로그만 남기도록 분리했다 — 일시적인 연결 끊김 같은, DB 커밋과 무관한 실패까지 전체 트랜잭션을 롤백시키지 않기 위해서다. `OutboxEventPublisherTest`에 성공/실패 두 경로를 각각 검증하는 테스트를 추가했다.

여러 애플리케이션 인스턴스가 같은 아웃박스 테이블을 동시에 폴링할 때 같은 행을 중복 처리할 수 있는 문제(행 잠금 없음)는 이번 결정 범위에 포함하지 않았다 — 다음 Step에서 폴링 방식 자체가 실제 메시지 브로커로 대체될 예정이라, 곧 사라질 코드에 클레임 로직을 미리 얹는 것은 과설계로 판단했다.

# 중복 로직 리팩토링

## 대상 범위
`src/main/java`, `src/test/java` 전체(Phase 1~2 시점 코드)를 대상으로, 같은 클래스 또는 같은 패키지 안에서 반복되는 로직/픽스처를 점검했다.

## 발견 및 조치

### 1. `OrderFacade`의 주문 조회 중복
`getOrder()`와 `confirmPayment()`가 각각 `orderRepository.findById(orderId).orElseThrow(() -> new BusinessException(OrderErrorCode.ORDER_NOT_FOUND))`를 동일하게 반복하고 있었다.

- 조치: `private Order findOrderOrThrow(Long orderId)` 헬퍼를 추가하고 두 메서드가 공유하도록 정리했다.
- `AuthService`, `ProductService`에도 `orElseThrow` 패턴이 각각 한 번씩 존재하지만, 같은 클래스 내부에 반복이 없어 대상에서 제외했다. 도메인이 다른 세 클래스(`OrderFacade`/`AuthService`/`ProductService`)를 하나의 공용 `findOrThrow` 유틸로 묶는 것은 각 도메인의 에러 코드가 서로 달라 제네릭화 이득보다 결합도만 늘어나므로 하지 않았다.

### 2. `domain/order` 테스트 픽스처 중복
`OrderTest`, `OrderFacadeTest`가 완전히 동일한 `newUser()`/`newProduct()` private 메서드를 각자 갖고 있었고, `OrderItemTest`/`OrderRepositoryTest`/`OrderFacadeTransactionTest`도 같은 형태의 `User`/`Product` 빌더 블록을 인라인으로 반복하고 있었다.

- 조치: 패키지 전용(package-private) `OrderTestFixtures` 클래스를 추가해 `newUser()`/`newProduct()`를 한 곳에 두고, 다섯 개 테스트 클래스가 정적 임포트로 공유하도록 정리했다.
- `OrderFacadeTransactionTest`는 이메일 유니크 제약 때문에 `System.nanoTime()`으로 이메일을 매번 다르게 만드는 `User`는 그대로 인라인으로 남겨뒀다. 겉보기엔 비슷해도 "매번 달라야 하는 값"이라 픽스처로 고정할 수 없는 경우라 억지로 통합하지 않았다.

### 3. `domain/product` 테스트 내부 반복
`ProductTest`가 `stock` 값만 다른 동일한 `Product.builder()` 블록을 4번, `ProductServiceTest`가 완전히 동일한 블록을 2번 반복하고 있었다.

- 조치: 패키지 전용 `ProductTestFixtures.newProduct(int stock)`를 추가해 두 클래스 모두 이 팩토리 메서드로 교체했다.

### 4. `domain/user` 테스트 내부 반복
`AuthServiceTest`가 이메일만 다른 동일한 `User.builder()` 블록을 2번, `UserRepositoryTest`가 이메일만 다른 블록을 3번 반복하고 있었다.

- 조치: 패키지 전용 `UserTestFixtures.newUser(String email, String password)`를 추가해 두 클래스 모두 이 팩토리 메서드로 교체했다. `AuthServiceTest`는 인코딩된 비밀번호(`"encoded-password"`)를, `UserRepositoryTest`는 평문 비밀번호(`"plain1234!"`)를 넘기도록 값만 다르게 호출한다.

## 의도적으로 통합하지 않은 부분

> [!NOTE]
> `OrderTestFixtures.newUser()`와 `UserTestFixtures.newUser()`는 필드 값이 사실상 동일하다. 그럼에도 두 클래스를 하나로 합치지 않았다.

`Order` 도메인의 테스트가 `User` 도메인의 테스트 전용 클래스를 참조하게 만들면, 프로덕션 코드에서는 없는 "테스트 코드 간 패키지 경계 침범"이 생긴다. 각 패키지의 테스트 픽스처는 그 패키지가 스스로 소유하고, 필요한 연관 엔티티(`Order`가 필요로 하는 `User`)는 자기 테스트 안에 최소한으로 다시 선언하는 쪽을 선택했다. 값이 우연히 같다고 그 자체를 공유 대상으로 삼으면, 이후 두 도메인의 테스트 요구사항이 갈라질 때(예: `Order` 쪽 `User` 픽스처에만 필드가 추가로 필요해지는 경우) 서로 발목을 잡는 결합이 생긴다.

## 검증
- `./gradlew compileJava compileTestJava` — 컴파일 통과
- `./gradlew test` (로컬 MySQL 컨테이너 기동 상태, `OrderRepositoryTest`/`OrderFacadeTransactionTest`/`UserRepositoryTest` 포함 전체) — 전부 통과, 회귀 없음

Evo-Commerce는 타임세일 같은 순간 트래픽 상황에서 실제로 터지는 동시성·정합성 문제를 직접 재현하고 해결한 이커머스 백엔드 프로젝트입니다. Toss Payments 결제 연동, Redis 분산락 기반 타임세일 참여 제어, Master/Slave DB 라우팅, Outbox 패턴 기반 결제-알림 이벤트 처리를 구현했습니다.

Case 01 · Concurrency Control

체크는 통과했는데, 왜 10명 다 참여됐지

TimeSaleParticipation · Redisson RLock · @Version
문제 상황

선착순 participantLimit을 초과하면 안 되는데, COUNT로 상한을 확인한 뒤 저장하는 구조에서 상한 3명 이벤트에 10명이 동시 참여하자 매번 10명 전원이 성공했습니다.

expected: 3
but was: 10

COUNT·INSERT가 원자적으로 묶이지 않은 check-then-act 문제였습니다. 트랜잭션 원자성과 여러 트랜잭션 간 상호 배제는 다른 개념이라, REPEATABLE READ 아래 10개 트랜잭션 모두 count = 0을 보고 통과했습니다.

검토한 대안
비관적 락SELECT FOR UPDATE
조회 시점에 행을 잠가 접근을 막지만, 락을 쥔 트랜잭션이 끝날 때까지 나머지가 커넥션을 붙든 채 대기해야 해서 커넥션 풀 고갈 위험으로 기각.
낙관적 락@Version + 재시도
1단계로 적용했지만 재시도 없이는 데드락, 재시도를 붙이면 정합성은 맞아도 롤백·백오프로 느려짐.
Redis 분산락Redisson RLock✓ 채택
이벤트별 락으로 동시 접근 자체를 차단해 MySQL은 애초에 동시 쓰기 경합을 겪지 않음.
적용한 해결책 & 결과

낙관적 락만 적용하자 동시 UPDATE가 InnoDB 잠금 순서를 꼬아 데드락이 나 1명만 성공했습니다. @Retryable + 지수 백오프를 추가해 정합성은 맞췄지만 평균 596ms가 걸렸습니다. 최종적으로 이벤트별 락 키(time-sale:participation-lock:{eventId})를 쓰는 Redisson 분산락으로 교체했습니다. TransactionTemplate으로 커밋 이후에만 unlock()하도록 순서를 맞췄고, @Version은 마지막 방어선으로 남겼습니다.

3회 반복 측정 결과 두 전략 모두 3/3 정합성을 지켰지만, Redis 분산락(169ms)이 낙관적 락+재시도(596ms)보다 약 3.5배 빨랐습니다. 분산락은 임계 구역에 한 번에 하나만 들여보내 MySQL이 쓰기 경합 자체를 겪지 않기 때문입니다.

일반화: 정합성을 지키는 전략과 그 부작용(데드락으로 인한 성공률 저하)은 따로 검증해야 합니다. "예외가 안 난다"가 아니라 "정원 안에서 최대한 많은 요청이 성공하는가"까지 측정해야 진짜 해결 여부를 알 수 있습니다.
Case 02 · Payment Idempotency

같은 웹훅이 두 번 오면 벌어지는 일

TossWebhookController · OrderFacade.handlePaymentWebhook
문제 상황

이미 PAID인 주문에 같은 결제완료 웹훅이 재전달되면 order.pay()가 매번 그대로 호출돼 INVALID_STATUS_TRANSITION 예외로 실패했습니다. Toss는 200이 아니면 계속 재전송하므로 같은 오류가 끝없이 반복됐습니다.

검토한 대안
멱등성 키이벤트 ID 이력 테이블
고유 ID를 부여하고 처리 이력을 별도 테이블에 기록. 웹훅 부수효과가 여러 개로 늘어날 때 필요해지는 방식.
목표 상태 확인Order.status 조회✓ 채택
이미 목표 상태(PAID)면 조용히 종료. 부수효과가 상태 전이뿐이라 별도 이력 테이블 없이도 안전.
적용한 해결책 & 결과

handlePaymentWebhook()이 order.pay() 호출 전에 order.getStatus() == PAID를 먼저 확인하도록 바꿨습니다. 같은 주문에 웹훅을 두 번 처리해도 두 번째 호출이 예외 없이 200으로 끝나는 것을 회귀 테스트로 검증했습니다.

스코프 노트: 이미 CANCELLED인 주문에 결제완료 웹훅이 오는 경우는 결제·취소가 경쟁하는 별도의 정합성 문제라 이번 수정 범위 밖으로 명시하고 남겨뒀습니다.
Case 03 · Architecture Enforcement

패키지를 나눠도 아무도 막아주지 않는다

ArchUnit · PackageArchitectureTest
문제 상황

도메인 패키지를 presentation/application/domain 계층으로 나눴는데도, 다른 도메인의 표현 계층이 이 도메인의 도메인 계층을 직접 참조하는 코드가 경고 없이 컴파일됐습니다.

import com.evo.commerce.domain.order.domain.OrderRepository;

public class ProductController {
    private final OrderRepository orderRepository; // 컴파일 에러도, 경고도 없다
}

Java의 패키지는 이름 규칙일 뿐, public class는 어떤 패키지에서든 import할 수 있습니다.

검토한 대안
package-private접근 제한자
같은 도메인 내부 허용 + 다른 도메인 표현 계층만 차단하는 세밀한 규칙을 표현할 수 없어 기각.
멀티모듈 / JPMS물리적 컴파일 경계
원천 차단 가능하지만, 도메인 4개 규모에 모듈 경계를 새로 설계·유지하는 비용이 이득보다 큼.
ArchUnit테스트 기반 강제✓ 채택
"이 패키지는 저 패키지에 의존 금지"를 테스트 코드로 표현. 구조 변경 없이 위반 시 테스트 실패.
적용한 해결책 & 결과

규칙 적용 중 @RequireRole(UserRole.MASTER)처럼 도메인 enum을 애너테이션 값으로 받는 것도 "타입 참조"로 취급된다는 새 위반을 잡았습니다. UserRole 대신 String으로 바꿔 결합을 없앴습니다. Spring Security가 enum 대신 문자열로 역할을 표현하는 것도 같은 이유입니다.

일반화: 폴더 재배치와 "아키텍처 규칙 강제"는 서로 다른 문제입니다. 전자는 후자의 필요조건이지 충분조건이 아닙니다. 좋은 제약은 문제를 감추는 대신 드러냅니다.

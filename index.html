Evo-Commerce는 타임세일 같은 순간 트래픽 상황에서 실제로 터지는 동시성·정합성 문제를 직접 재현하고 해결한 이커머스 백엔드 프로젝트입니다. Toss Payments 결제 연동, Redis 분산락 기반 타임세일 참여 제어, Master/Slave DB 라우팅, Outbox 패턴 기반 결제-알림 이벤트 처리를 구현했습니다.

아래는 그 과정에서 마주친 세 가지 기술적 문제를 문제 상황 → 검토한 대안 → 적용한 해결책 → 결과 순서로 정리한 것입니다. 트러블슈팅 내용을 정리한 상세 기록은 아래 링크에서 확인할 수 있습니다.

Case 01 · Concurrency Control

체크는 통과했는데, 왜 10명 다 참여됐지

TimeSaleParticipation · Redisson RLock · @Version
문제 상황

선착순 participantLimit을 초과해 참여 기록이 저장되면 안 됩니다. 참여자 수를 COUNT로 조회해 상한과 비교한 뒤 저장하는 구조였는데, 상한 3명인 이벤트에 10명이 동시에 참여를 시도하자 매번 10명 전원이 성공했습니다.

$ ./gradlew test --tests "*선착순*"

동시에_여러_명이_참여해도_선착순_인원_제한을_초과하지_않는다() FAILED
    org.opentest4j.AssertionFailedError:
        expected: 3
         but was: 10
원인

COUNT 조회와 INSERT 저장이 하나의 원자적 연산으로 묶여 있지 않았습니다 — check-then-act. 트랜잭션의 원자성(내 SQL이 전부 성공하거나 전부 취소됨)과 여러 트랜잭션 사이의 상호 배제(내가 처리하는 동안 남이 못 끼어듦)는 다른 성질이고, 트랜잭션 경계는 후자를 보장하지 않습니다. REPEATABLE READ 아래서 동시에 시작된 10개 트랜잭션 전부가 count = 0을 보고 상한 검사를 통과했습니다.

검토한 대안
비관적 락SELECT FOR UPDATE
조회 시점에 행을 잠가 접근 자체를 막습니다. 경합이 몰리는 순간엔 확실하지만, 락을 쥔 트랜잭션이 끝날 때까지 나머지가 커넥션을 붙든 채 대기해야 해서 커넥션 풀 고갈 위험으로 기각했습니다.
낙관적 락@Version + 재시도
평소엔 락 없이 저장 시점에 충돌만 감지해 재시도합니다. 1단계로 적용했지만 재시도 없이는 데드락이 발생했고, 재시도를 붙이면 정합성은 맞아도 롤백·백오프로 느려졌습니다.
Redis 분산락Redisson RLock✓ 채택
애플리케이션 레이어에서 이벤트별 락을 걸어 동시 접근 자체를 차단합니다. MySQL은 애초에 동시 쓰기 경합을 겪지 않습니다.
적용한 해결책

1단계 낙관적 락만 적용하자 10개 트랜잭션의 동시 UPDATE가 InnoDB 행 잠금 순서를 꼬아 데드락을 냈습니다 — 정원 3명 중 1명만 성공했습니다. 2단계로 @Retryable + 지수 백오프(50ms→500ms)를 추가해 정합성을 맞췄지만, 매 시도마다 새 트랜잭션을 여느라 평균 596ms가 걸렸습니다. 3단계로 이벤트별 락 키(time-sale:participation-lock:{eventId})를 쓰는 Redisson 분산락으로 교체했습니다. 락 해제가 커밋보다 먼저 일어나면 다음 스레드가 반영 전 값을 읽으므로, TransactionTemplate으로 커밋이 끝난 뒤에만 unlock()하도록 순서를 맞췄습니다. @Version은 락 오구현 시의 마지막 방어선으로 남겨뒀습니다.

결과 — 상한 3명 · 동시 요청 10건, 3회 반복 측정
두 전략 모두 정합성은 3/3으로 동일합니다. Redis 분산락이 약 3.5배 빠릅니다 — 낙관적 락+재시도는 10건 전부를 MySQL까지 들여보낸 뒤 대부분을 롤백·백오프시키는 반면, 분산락은 한 번에 한 요청만 임계 구역에 들여보내 MySQL이 애초에 쓰기 경합을 겪지 않습니다.
일반화 — 정합성을 지키는 전략과 그 전략의 부작용(데드락으로 인한 성공률 저하)은 따로 검증해야 합니다. "예외가 안 난다"가 아니라 "정원 안에서 최대한 많은 요청이 성공하는가"까지 같은 시나리오로 직접 측정해야 진짜 해결 여부를 알 수 있습니다.
Case 02 · Payment Idempotency

같은 웹훅이 두 번 오면 벌어지는 일

TossWebhookController · OrderFacade.handlePaymentWebhook
문제 상황

이미 결제가 완료돼 PAID인 주문에 같은 결제완료 웹훅이 재전달되면, order.pay()가 매번 그대로 호출돼 INVALID_STATUS_TRANSITION 예외로 실패했습니다. Toss는 200이 아닌 응답을 실패로 간주해 계속 재전송하므로, 같은 오류가 끝없이 반복됐습니다.

검토한 대안
멱등성 키이벤트 ID 이력 테이블
이벤트에 고유 ID를 부여하고 처리 이력을 별도 테이블에 기록해 중복 수신을 추적합니다. 웹훅의 부수효과가 여러 개로 늘어날 때 필요해지는 방식입니다.
목표 상태 확인Order.status 조회✓ 채택
처리 전에 주문이 이미 목표 상태(PAID)인지 확인해, 같으면 조용히 종료합니다. 지금 웹훅의 유일한 부수효과가 상태 전이뿐이라 별도 이력 테이블 없이도 안전합니다.
적용한 해결책 & 결과

handlePaymentWebhook()이 order.pay()를 호출하기 전에 order.getStatus() == PAID인지 먼저 확인하고, 이미 PAID면 그대로 반환하도록 바꿨습니다. 같은 주문에 웹훅을 두 번 처리해도 두 번째 호출은 예외 없이 200으로 끝나는 것을 회귀 테스트로 검증했습니다.

스코프 노트 — 이미 CANCELLED인 주문에 결제완료 웹훅이 오는 경우는 이번 수정에 포함하지 않았습니다. 이건 "정상적인 중복 수신"이 아니라 결제와 취소가 경쟁하는 별도의 정합성 문제라 범위 밖으로 명시하고 남겨뒀습니다.
Case 03 · Architecture Enforcement

패키지를 나눠도 아무도 막아주지 않는다

ArchUnit · PackageArchitectureTest
문제 상황

도메인 패키지 내부를 presentation / application / domain 계층으로 나눴는데도, 다른 도메인의 표현 계층이 이 도메인의 도메인 계층을 직접 참조하는 코드가 아무 경고 없이 컴파일됐습니다.

package com.evo.commerce.domain.product.presentation;

import com.evo.commerce.domain.order.domain.OrderRepository; // 막고 싶었던 참조

public class ProductController {
    private final OrderRepository orderRepository; // 컴파일 에러도, 경고도 없다
}

Java의 패키지는 이름 규칙일 뿐 접근을 물리적으로 차단하는 장치가 아닙니다. public class는 어떤 패키지에서든 import할 수 있습니다.

검토한 대안
package-private접근 제한자
같은 도메인 내부는 허용하고 다른 도메인의 표현 계층만 막는, 세밀한 규칙을 표현할 수 없어 기각했습니다.
멀티모듈 / JPMS물리적 컴파일 경계
실수 자체를 원천 차단할 수 있지만, 도메인 4개 규모에 모듈 경계를 새로 설계·유지하는 비용이 이득보다 크다고 판단했습니다.
ArchUnit테스트 기반 강제✓ 채택
"이 패키지는 저 패키지에 의존하면 안 된다"를 테스트 코드로 표현합니다. 물리적 구조를 바꾸지 않고도 세밀한 규칙을 표현하고, 위반 시 테스트가 실패합니다.
적용한 해결책

규칙을 적용하는 과정에서 새 위반을 하나 더 잡았습니다. @RequireRole(UserRole.MASTER)처럼 도메인 enum을 애너테이션 값으로 받는 것도 "그 타입을 참조하는 것"으로 취급돼, 표현 계층이 다른 도메인의 enum을 import하는 결합이 생겼습니다. UserRole 대신 String 값을 받도록 바꿔 결합을 없앴습니다 — Spring Security의 @PreAuthorize("hasRole('MASTER')")가 enum 대신 문자열을 쓰는 것도 같은 이유입니다.

일반화 — 폴더 재배치와 "아키텍처 규칙을 강제하는 것"은 서로 다른 문제입니다. 전자는 후자의 필요조건이지 충분조건이 아닙니다. 좋은 제약은 문제를 감추는 대신 드러냅니다 — 규칙이 생기자마자 "이 결합이 정말 필요한가"를 다시 묻게 됐습니다.

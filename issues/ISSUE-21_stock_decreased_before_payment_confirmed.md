# [Bug] 결제 승인 전에 상품 재고가 먼저 차감됨

### 증상
- 상품 상세에서 "주문하기"를 눌러 주문만 생성해도(`POST /api/orders`) 실제 결제를 완료하기 전에 해당 상품의 재고가 즉시 줄어든다.
- Toss 결제창을 닫거나 결제에 실패해서 결제를 끝내지 않아도, 이미 줄어든 재고는 복구되지 않고 그대로 남는다.
- 반복해서 주문만 생성하고 결제를 완료하지 않으면 재고가 계속 줄어들어, 실제로는 아무도 구매하지 않았는데도 상품이 품절 상태가 될 수 있다.

### 환경
- `src/main/java/com/evo/commerce/domain/order/application/OrderFacade.java`
- `src/main/java/com/evo/commerce/domain/product/domain/Product.java`
- `src/main/resources/static/product-detail.html`, `checkout.html`

### 재현 절차
1. 재고가 있는 상품 상세 페이지에서 수량을 지정하고 "주문하기"를 클릭한다. (`POST /api/orders` 호출 → `OrderFacade.placeOrder()`)
2. 상품 목록/상세를 다시 조회해 재고가 이미 줄어든 것을 확인한다.
3. 결제 페이지(`checkout.html`)로 넘어간 뒤 "결제하기"를 누르지 않거나 Toss 결제창을 닫아 결제를 완료하지 않는다.
4. 상품 재고를 다시 조회해도 2번에서 줄어든 재고가 복구되지 않는다. 해당 주문은 `orders.status = CREATED`로 영구히 남는다.

### 관찰
- `OrderFacade.placeOrder()`가 각 주문 아이템에 대해 `product.decreaseStock(quantity)`를 즉시 호출해, 주문이 생성되는 시점(결제 승인 이전)에 재고 UPDATE가 커밋된다.
- 반면 주문 상태를 `PAID`로 바꾸는 `order.pay()`는 별도의 `confirmPayment()`에서, 실제 Toss 결제 승인(`tossPaymentClient.confirm()`)에 성공한 뒤에만 호출된다.
- 즉 "재고 차감"과 "결제 승인"이 서로 다른 시점에 일어나는데, 재고 차감이 결제 승인보다 먼저, 그것도 결제 성공 여부와 무관하게 실행된다.
- 주문을 취소하거나 재고를 되돌리는 로직(`Order.cancel()`, `Product.increaseStock()`)은 엔티티에 정의만 되어 있을 뿐 어디에서도 호출되지 않는다. 그래서 결제를 끝내지 않은 주문의 재고는 영구히 복구되지 않는다.

### 상태
`[CLOSED]`

### 원인 분석
`placeOrder()`가 "주문 생성"과 "재고 확정 차감"을 같은 트랜잭션에서 함께 처리하도록 작성되어 있었다. 이는 사용자가 상품 상세에서 "주문하기"를 누르는 즉시 재고를 차감하는 흐름으로, 실제로 돈을 지불했는지 여부와 재고 차감 시점이 완전히 분리되어 있었다. Toss 연동을 도입하면서 결제 승인 성공 여부에 따라 주문 상태(`PAID`)를 결정하는 `confirmPayment()`는 별도로 분리됐지만, 재고 차감 로직은 원래 있던 `placeOrder()`에 그대로 남아 함께 옮겨지지 않았다. 그 결과 주문 상태는 결제 승인 시점에 확정되는데 재고는 주문 생성 시점에 이미 확정되어 있는 불일치가 생겼다.

### 해결 방안
재고를 실제로 차감하는 시점을 주문 생성(`placeOrder`)에서 결제 승인이 확정되는 시점(`confirmPayment`, 그리고 Toss 웹훅으로 결제 완료를 통지받는 `handlePaymentWebhook`)으로 옮겼다. 대신 주문 생성 시점에는 재고가 애초에 부족한 주문을 미리 걸러내기 위해, 재고를 변경하지 않고 확인만 하는 `Product.validateStockAvailable(quantity)`를 새로 분리해서 호출한다. `decreaseStock()`도 내부적으로 이 검증 메서드를 재사용하도록 정리해, 같은 재고 부족 검증 로직이 두 곳에 중복되지 않게 했다.

이제 결제를 끝내지 않고 이탈한 주문은 재고에 전혀 영향을 주지 않는다. 다만 이 수정이 "주문 생성 시점의 재고 검증"과 "결제 승인 시점의 재고 차감" 사이에 다른 사용자가 끼어드는 동시성 문제까지 해결하지는 않는다(예: 마지막 1개 재고를 두 사용자가 거의 동시에 주문 생성까지는 통과하고, 그중 결제를 먼저 완료한 쪽만 재고를 차감받고 나머지는 결제 승인 시점에 재고 부족 예외를 받는 상황).

> [!NOTE]
> 여러 사용자가 동시에 같은 상품을 주문하는 상황의 재고 동시성 제어(비관적/낙관적 락, 분산 락 등)는 이 이슈의 범위 밖이며 별도로 다룬다.

회귀 테스트로 `OrderFacadeTest`에 "결제 승인 시점에 재고가 차감된다", "결제 승인 시점에 재고가 부족하면 예외가 발생한다" 케이스를 추가했고, `OrderFacadeTransactionTest`로 주문 생성만으로는 DB 재고가 변하지 않음을 실제 DB 연동으로 확인했다. `ProductTest`에는 `validateStockAvailable()`이 재고를 변경하지 않고 검증만 한다는 케이스를 추가했다.
